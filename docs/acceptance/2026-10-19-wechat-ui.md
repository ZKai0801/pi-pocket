## Findings

### F1 — the editor's 取消/保存 row sat under the tab bar (blocker, fixed)

`src/components/connections/ConnectionsList.vue`. The editor card is taller than
the shell's content box, `.phone-shell__content` is `overflow: hidden`, and
`.connections` was neither height-constrained nor scrollable. The action row
therefore fell into the clipped area behind the fixed `.app-tab-bar`
(`z-index: 20`), and a tap aimed at 保存 hit the tab bar instead: `06-tap-through-tabbar.png`
shows the app on the 会话 tab after a tap at the 保存 button, with the editor
still open behind it. The sheet did not scroll either (three different swipe
gestures produced an identical frame), so 保存 was unreachable by touch on a
360 dp-wide phone.

Fix: `.connections--editing` (`height: 100%`, `box-sizing: border-box`,
`overflow-y: auto`) scoped to the editor state, so only the editor scrolls.
`11-editor-fixed.png` shows 取消 / 保存 fully above the tab bar; `14-host-saved.png`
is the save that followed.

### F2 — the row menu was clipped to a sliver (blocker, fixed)

`src/components/connections/ConnectionsList.vue`. `.connections__list` clips to
its rounded card (`overflow: hidden`, pre-existing at `60eb063`), and
`.connections__menu` is an absolutely positioned child that hangs *below* its
row, so 编辑 / 删除 were cut down to a 2 px strip (captured before the fix;
`.connections__more` and the menu are at `ConnectionsList.vue:271`/`279`).
Consequence: a saved host could not be edited or deleted on the packaged build.

Fix: `.connections__list--menu-open { overflow: visible }`, applied only while
`menuFor` is set, placed after the base rule so equal specificity resolves in
the open state's favour. `18-menu.png` shows the full 编辑 / 删除 menu, and
`19-edit-saved-credential.png` is the editor it opens.

### F3 — a key host cannot be created in the packaged app (blocker, fixed in Plan 6)

**Fixed.** Plan 5b Task 1 made `SshKeysScreen` reachable from the connection
editor as a 管理密钥 sheet, and the 2026-10-21 re-acceptance walked it on the
device — see `2026-10-21-wechat-ui-rerun.md`, screenshots 31–35, 45 and 50–52,
where a key host is created and saved. The finding below is kept as the record
of what the 2026-10-19 build did.

`02-editor-key.png`: the 密钥 select says 密钥库为空 – 先在密钥页导入一把密钥, but the
phone shell mounts only 连接 / 项目 / 会话 (`src/phone/PhoneApp.vue`,
`src/components/shell/AppTabBar.vue`); `SshKeysScreen.vue` exists in the tree but
is not mounted by any route. So the instruction points at a screen the shipped
app does not have, and every key-based acceptance item (2, 8) is unreachable.

This is a product gap, not a test gap: it is the same class of dead surface that
Plan 5 Task 3 removed from `androidTest`. It needs a decision — mount a key page
or import sheet, or seed the vault from another entry point — before items 2 and
8 can be accepted.

### F4 — user-visible errors are English in a Chinese UI (fixed in Plan 6, minor)

`12-validation-english.png` shows **Give the host a name.** under a form whose
labels are 名称 / 主机 / IP; `15-connect-error.png` shows **The connection to
"test-host" did not open.** Both strings reach the user untranslated. The
existing `releaseChrome` guard only bans PTY/SSH-internal jargon, so it does not
catch this.

### F5 — a validation error outlives the field it complains about (fixed in Plan 6, minor)

Filling 名称 after **Give the host a name.** leaves the message on screen until
the next submit (`13-filled` was captured during the walk; the frame after
filling all three fields still carries the message). Cosmetic, but it reads as
"still wrong" while the form is correct.

## What this walk does not prove

- **The 0.5.x → 0.6.0 upgrade path is not proven, and is currently unresolved.**
  `runInstalledDataMigration` (`src/migration/installedDataMigration.ts:857`) is
  reached only from `src/App.vue:1441`/`:1321` (the unmounted legacy shell) and
  `src/sharedApp/main.ts:33` (no build entry), so no reachable entry point runs
  it — a user upgrading in place would find their hosts listed but with no trust
  pins, an empty key vault and default preferences. Whether that is in scope is a
  maintainer decision, recorded with its evidence in
  `.superpowers/sdd/2026-10-19-phone-shell-tabs-chat/migration-question.md`; this
  record takes no position.
- Nothing about a real SSH session: host-key trust, key auth, password auth
  against a real server, Pi project discovery, session listing, chat send,
  terminal attach and reconnect are all **unverified** on this build.
- Nothing about the visual parity against the spec's chat mockup (§5/§10): the
  chat screen was never reached (item 4 NOT ACCEPTED), so the side-by-side
  comparison the plan asks for cannot be made yet.
- The password credential is proven *sealed and referenced* (lock glyph, 已保存,
  清除已保存凭据 clears it — `19-edit-saved-credential.png`, `20-after-clear.png`),
  but not proven *usable*: no server accepted it.
- Screenshots are from a phone-sized emulator at 420 dpi; no tablet or foldable
  layout was exercised.
